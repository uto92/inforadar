# 実機データによる v1 パーサ検証レポート

- **検証日**: 2026-08-19
- **対象**: `cybernetics-v1`（`platform/src/parser/cybernetics_v1.ts`）
- **データ**: iOS プローブ `ios-probe/0.1.0` が読んだ実カード 1枚 / 20ブロック（読取 2026-08-11）

## 結論

1. **v1 の解釈は実データで成立している。** 20ブロックすべてを解釈でき、`unparsable` / `blank` はゼロ。
   残額と連番の整合を検算した14区間すべてで、差分が実際の運賃・物販・チャージとして妥当な額になった。
2. **受信側にバグが1件あり、修正済み。** 実機のペイロードはキー名が camelCase（`sessionId` /
   `records` など）で、修正前は HTTP 400 で全件弾かれていた。
3. **解釈側に v2 で決め直すべき点が3つ見つかった。** いずれも「v1 が間違っている」ではなく
   「v1 が置いた仮定が実データで初めて具体的な形になった」もの。生HEXは残っているので
   いつでも再解析できる（→ [v2 の検討事項](#v2-の検討事項判断待ち)）。

## 1. 検証に使ったデータ

| 項目 | 値 |
|---|---|
| `client_version` | `ios-probe/0.1.0` |
| `read_at` | 2026-08-11T08:50:03+09:00 |
| ブロック数 | 20（すべて32桁HEX、空き枠なし） |
| `card_pseudonym` | 64桁hex（端末内HMAC） |

### このドキュメントに含まれるデータについて

検証の根拠として、**デコード結果（利用日・処理種別・駅コード・残額）は本文に載せている。**
数値を伏せると「解釈が正しいことの検算」が読み手に再現できないため。
一方、**生HEXと `card_pseudonym` は載せていない。**
一次情報は D1 の `raw_observations` にあり、そこから再解析できる
（それがこの基盤の設計前提そのものである）。

なお、このカードの被験者は開発者本人（P001）である。
他の被験者のデータを同じ形で文書化する場合は、公開範囲をあらためて判断すること。

## 2. 受信できなかった問題（修正済み）

実機のペイロードをそのまま `POST /v1/ingest` に投げると、修正前はこうなっていた。

```
HTTP 400 {"error":"invalid_payload","detail":"session_id must be a client-generated id ..."}
```

Swift の `JSONEncoder` は既定で camelCase を吐くため、実機は次の形で送っていた。

| 実機が送るキー | サーバが期待していたキー |
|---|---|
| `sessionId` | `session_id` |
| `cardPseudonym` | `card_pseudonym` |
| `deviceId` | `device_id` |
| `readAt` | `read_at` |
| `clientVersion` | `client_version` |
| `records` | `blocks` |

**キー名の違いで生データを落とすのは受信側の責務に反する**ため、
`src/ingest.ts` の入口で別名を吸収するようにした（snake_case / camelCase の混在も可）。
値の検証規則そのものは変更していない。

修正後、実機ペイロードは無変換で通る。

```json
{"status":"stored","stored_blocks":20,"rejected_blocks":[],
 "derived":{"rawRows":20,"uniqueBlocks":20,"derived":20,"blank":0,"unparsable":0}}
```

再送すると `duplicate_session` / `stored_blocks: 0` になることも確認した。

## 4. 検算: 残額チェーンは整合している

「残額 = offset 10-11 のリトルエンディアン」「連番 = offset 12-14」という v1 の仮定が
正しければ、連番順に並べた残額の差分は実際の金額として筋が通るはずである。

連番が連続する **14区間すべてで妥当**だった。

| 差分 | 内訳 | 判定の根拠 |
|---|---|---|
| **-2000** ×3 | チャージ（機器 = 携帯電話） | モバイルチャージの単位としてちょうど 2000円 |
| **230** ×2 | バス（車載端末） | 同一路線の同額運賃が2回 |
| **420 / 250** | 運賃支払 / バス | 鉄道・バス運賃として妥当 |
| **170 / 150 / 130** | 物販・自販機 | 飲料等の価格帯 |
| **226 / 1474 / 1516 / 1752** | 物販 | 物販なので額の幅は広い |

特に、**チャージがちょうど 2000円 の増加として3回とも現れた**ことが、
リトルエンディアン読みと連番順の両方を同時に裏付けている。
どちらかを取り違えていれば、この一致は起きない。

## 5. 連番には欠番が出る

保持していたのは **連番 17〜41 のうち 20件**。5件（18, 20, 22, 24, 32）が欠けていた。

つまり **カードの履歴枠に残らない取引が存在する**。20ブロックを読めば直近20件の
「取引」が揃う、という前提は成り立たない。

これは `amount_estimated` の設計判断を裏付ける結果でもある。
v1 は「連番が連続する区間だけ差分を計算し、飛んでいれば `null`」としている。
もし欠番を無視して差分を取っていれば、欠けた取引の分が合算された額を
「利用額」として記録してしまっていた。実データでも欠番の前後は正しく `null` になった。

> **研究上の含意**: 交通系ICカードの履歴は「その人の全移動」ではない。
> 欠落があることを前提に、GPS など他ソースと突き合わせる設計にしておくこと。

## 6. リージョンバイト（offset 15）に `0xA0` が出る

v1 は offset 15 をそのまま `area_code` として使い、駅コードを `AA-LL-SS` 形式で持つ。
実測値は2種類だった。

| offset 15 | 件数 | 出現する処理種別 |
|---|---:|---|
| `0x00` | 13 | 運賃支払, チャージ, 物販 |
| `0xA0` | 7 | 運賃支払, バス |

結果として駅コードが `A0-82-1E` のような値になる。
一般に流通している駅コード対応表の「エリアコード」は 0, 1, 2 … という小さな値域なので、
**`0xA0` をそのままエリアコードとして突き合わせることはできない。**

v1 はこれを承知のうえで「マスタに当たらなければコードのまま表示する」設計にしてあるため、
壊れてはいない。ただし正規の対応表を投入する段階で、対応付けを決め直す必要がある。

## 7. 物販レコードには時刻が入っている

v1 は物販系（処理種別 70/73/74/75/198/203）の offset 6-7 を「駅ではなく時刻」として
扱い、駅コードを付けない。実データでこの領域を **5bit(時) + 6bit(分)** として読むと、
すべて妥当な時刻になった。

| 連番 | 利用日 | 読めた時刻 | 機器種別 |
|---:|---|---|---|
| 17 | 2025-04-24 | 10:28 | 物販端末 |
| 27 | 2025-04-26 | 12:49 | 物販端末 |
| 28 | 2025-04-26 | 16:49 | 物販端末(0xCB) |
| 31 | 2025-04-27 | 22:17 | 物販端末 |
| 37 | 2025-05-01 | 12:18 | 物販端末 |
| 38 | 2025-05-01 | 12:19 | 自販機 |
| 39 | 2025-05-03 | 11:28 | 物販端末(0xC9) |
| 41 | 2026-07-01 | 09:48 | 自販機 |

連番 37→38 が **12:18 → 12:19** と1分差で連続しているのは、
「昼に物販端末で買い、直後に自販機で買った」という読み方と完全に整合する。
時刻として読めているという強い傍証になる。

> **これは履歴のなかで唯一、分単位の時刻が取れるレコード種別である。**
> 鉄道・バスの利用は日付までしか分からない。
> 現行スキーマに時刻列がないため、この値は保存していない。

## 8. レコードの「型」の観測

offset 2 / 3 / 15 の組み合わせには規則性があった。

| 処理種別 | offset2 | offset3 | offset15 | 件数 | 機器種別 |
|---|---|---|---|---:|---|
| 運賃支払(1) | `0x3F` | `0x02` | `0xA0` | 4 | `0x16` 改札機 |
| 運賃支払(1) | `0x00` | `0x02` | `0x00` | 1 | `0x16` 改札機 |
| チャージ(2) | `0x3F` | `0x00` | `0x00` | 4 | `0x1B` 携帯電話 |
| バス(15) | `0x3F` | `0x0F` | `0xA0` | 3 | `0x05` 車載端末 |
| 物販(70) | `0x00` | `0x00` | `0x00` | 8 | `0xC7` `0xC8` `0xC9` `0xCB` |

注目点:

- **同じ「運賃支払」に2種類の型がある。** 4件は offset2=`0x3F` / offset15=`0xA0`、
  1件（連番26）だけ offset2=`0x00` / offset15=`0x00` で、駅コードも `00-01-E8` と
  他の改札レコード（`A0-82-1E` 等）から大きく外れている。事業者の違いか、
  別種の入出場かは、このデータだけでは判断できない。
- offset2 = `0x3F` と offset15 = `0xA0` の出現がほぼ連動している。
  offset15 は「地域」ではなく、支払方法やカード種別に関する情報を含んでいる可能性がある。

いずれも**仮説の段階**であり、v1 の実装は変更していない。

## v2 の検討事項（判断待ち）

解釈の変更はすべて `PARSER_VERSION` を上げて `POST /v1/reparse` する案件であり、
研究者の判断事項として保留してある。生HEXは不変なので、いつ決めても全期間に遡及できる。

| # | 内容 | 影響 | 判断が要る理由 |
|---|---|---|---|
| 1 | **物販の時刻を保存する** | `derived_transactions` に列追加 + `PARSER_VERSION` | スキーマ変更を伴う。分単位の行動が研究上必要かどうか |
| 2 | **`area_code` の対応付けを決める** | 駅コードの表記が変わる | 正規の駅コード対応表を入手してからでないと決められない |
| 3 | **駅として解釈しない処理種別を広げる** | チャージ・バスの入出場欄が `null` になる | 現状 v1 は物販系のみ除外。チャージの offset 6-7 は全件 `60-FB` 固定で駅ではない |

**1 が行動研究として最も効く**と考えている（履歴で唯一の分単位データのため）。

# 実機ペイロード（camelCase のまま）をそのまま投入

  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d @device.json

  -H "Authorization: Bearer $TOKEN"

自動テストでも固定してある（`test/ingest.test.ts`）。
